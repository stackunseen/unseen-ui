# Permission requests and acknowledged handoffs

Both families retain `card`, `banner` and `compact`. The host owns authentication, authorization, immutable versions, receipt retention and execution. Local tests use synthetic host data; they do not verify production permission enforcement or durable transfers.

## Public imports and migration

```tsx
import {
  PermissionRequest,
  AgentHandoff,
  inspectPermissionSnapshot,
  inspectPermissionCommand,
  inspectPermissionReceipt,
  validatePermissionDecision,
  inspectHandoffSnapshot,
  inspectHandoffCommand,
  inspectHandoffReceipt,
  validateHandoffDecision,
  type ScopedPermissionRequestProps,
  type ScopedAgentHandoffProps,
  type PermissionSnapshot,
  type PermissionDecisionCommand,
  type PermissionReceipt,
  type PermissionSubmission,
  type HandoffSnapshot,
  type HandoffDecisionCommand,
  type HandoffReceipt,
  type HandoffSubmission,
} from '@stackunseen/ui';
```

The root is a React client entry. Its inspection helpers validate presentation data and compare exact command identity. Server authorization belongs to the host. Core remains independent of React; use its pure adapter on a server where appropriate and enforce domain invariants at the authoritative host boundary. Neither component implements provider connections, networking or persistence.

Legacy permission props (`resource`, `scopes`, `status`, `pending`, boolean `onDecision`) and legacy handoff props (`HandoffRequest`, two-argument `onDecision`) retain behavior and callback inference. They are deprecated for integrations requiring exact receipts. Legacy props cannot establish the new provenance guarantees. Opt into the scoped overload by supplying `value`, `commandId` and `submission`; handoff `value` then has the `HandoffSnapshot` shape. Do not mix scoped and legacy props.

`PermissionRequestProps` and `AgentHandoffProps` are unions. Prefer the explicit `Scoped*Props` or `Legacy*Props` names in wrapper components: TypeScript utilities on overloaded functions select the last overload.

## Controlled usage

The following wrappers preserve host ownership and work with every presentation. The component emits a frozen copy of the exact command; the caller must retain it before dispatch and promptly render `submitting`. `commandId` is a host-allocated idempotency key, not generated by the component.

```tsx
function PermissionExample(props: ScopedPermissionRequestProps) {
  return <PermissionRequest {...props} variant="card" headingLevel={3} />;
}

function HandoffExample(props: ScopedAgentHandoffProps) {
  return <AgentHandoff {...props} variant="banner" />;
}

// Host/controller handlers, not component-local authoritative state:
// onDecision(original): retain {state: 'submitting', original}, then dispatch once.
// onReconcile(original): look up that exact original; never dispatch it again.
// reconciling: true disables repeated lookup while the host awaits the lookup response.
```

The [decision fixtures](../tests/decision-fixtures.ts) contain complete synthetic snapshots, commands and applied receipts. Use their shapes with the public types; do not import test fixtures into an application.

## Exact targets and current snapshots

Every target includes the core adapter's workspace/optional branch/thread/run/attempt/stream/schema scope, `runVersion`, an immutable request `version` and `expiresAt`. Identity strings are nonblank, at most 160 UTF-16 units and exclude control/surrogate characters. Scope arrays contain 1–50 unique nonblank items. Equality preserves scope-array order; reordering requires a replacement target/version. Expiry uses a finite parsed timestamp and is checked again synchronously before a callback.

Server and initial hydration markup keep decisions disabled until the client checks time. The initial HTML therefore stays stable if expiry crosses between rendering and hydration. This is an availability guard; the authoritative host still checks its own clock.

| Family | Additional target bindings | Current host state |
| --- | --- | --- |
| Permission | `requestId`, `subjectId`, `resource`, exact `scopes`, `accessVersion` | `status`, `freshness`, decision `access`, optional acknowledged `grant` |
| Handoff | `handoffId`, distinct `from`/`to`, `ownershipVersion`, `snapshotVersion`, exact `context`, `scopes`, `accessVersion` | `status`, `freshness`, acknowledged/unknown `ownership`, recipient `access`, public `summary` |

Permission status is `requested`, `granted`, `denied`, `revoked`, `expired` or `unknown`. A granted snapshot must supply grant identity/version and who acknowledged it, when. Decision access is distinct from the resulting permission. Its `subjectId`/`version` must match the target subject/access revision.

Handoff status is `requested`, `accepted`, `declined`, `expired`, `cancelled`, `denied`, `revoked` or `unknown`. Ownership is either `{state: 'unknown'}` or `{state: 'acknowledged', ownerId, version, acknowledged: {by, at}}`. The recipient is never inferred to own work because a button was clicked, a command was received or a request says accepted. A current acknowledged ownership snapshot is the display authority. Stale/unknown freshness labels it as the last acknowledged owner.

Context provenance binds `id`, `version`, `sourceId`, `sourceVersion` and `providedBy`. The host owns immutable content at those references; changing summary/source content requires replacement versions. The summary is public inert text, bounded to 10,000 UTF-16 units. Recipient access identifies `subjectId`, `version`, `checkedBy`, `checkedAt` and `available | denied | revoked | unknown`. Access subject/version must match the requested recipient and target access revision. Summary and source details disappear when access is unavailable or handoff status is denied/revoked/unknown; historical receipt lookup remains independent.

New decisions require an idle submission, current freshness, requested status, available decision/recipient access, complete valid target/command identity and unexpired request. Handoff also requires the acknowledged owner and ownership revision to match the sender and target. Every retained original—including `failed`—blocks a new decision until the host explicitly supplies a reconciled replacement/idle record. Components do not clear originals on refresh or automatically retry mutations.

## Submission and exact-original receipts

`PermissionSubmission` and `HandoffSubmission` are `{state: 'idle'}` or `{state, original, receipt?}`. Non-idle state is the existing core submission vocabulary: `submitting`, `acknowledged`, `failed`, `outcome-unknown`. The receipt and current snapshot are separate facts. Missing receipt is never fabricated from `acknowledged`.

| Receipt outcome | Meaning and UI behavior |
| --- | --- |
| `accepted` | Host received the original command; effect still unconfirmed. Lookup stays available. |
| `unknown` | Outcome remains unknown. Preserve original and lookup only. |
| `not-found` | Lookup did not find this original; not proof that it never executed. No automatic resend. |
| `rejected` | Host rejected this original. A new decision requires deliberate host-provided current state. |
| `applied` | Host confirms this exact decision's historical effect, with required acknowledgement/result fields. It never overwrites a newer current snapshot. |

Every receipt embeds the full original `commandId`, target and decision. Same command ID with a different target/decision is rejected. `inspectPermissionReceipt(original, candidate)` and `inspectHandoffReceipt(original, candidate)` return a bounded immutable matching receipt or `undefined`. A malformed or mismatched receipt cannot establish success; ordinary bounded malformed receipt data retains the original for lookup. An entirely malformed/excessive submission fails closed and requires host recovery outside the invalid record.

Permission applied receipts require `permission` to match allow/granted or deny/denied, host acknowledgement, and a grant identity/version only for a grant. Handoff applied receipts require the original decision, exact context/access revision and acknowledgement by the requested recipient. Acceptance requires that recipient as resulting owner and a changed ownership revision; decline retains sender and ownership revision. These are consistency checks on host assertions, not proof of authentic identity or a durable database transaction.

Inspection bounds plain data before schema traversal, copies descriptor values and freezes only the copy. Ordinary accessors, cycles, sparse arrays and excessive data are rejected. Reflection on arbitrary hostile Proxies is not process isolation. Snapshot/receipt text is React text; neither component evaluates content or follows source-supplied instructions.

## Host integration

Authenticate the actor, authorize the exact current scope, verify expiry/access/ownership/context revisions, deduplicate exact immutable commands and commit the authoritative effect with its original receipt. Define receipt retention and authorization for historical lookup. Current revocation must not be undone by an old applied receipt. Two actors racing an ownership revision must produce at most one accepted transfer at the host. Refresh alone does not settle a lost acknowledgement.

The library does not provide durable receipt storage, automatic retries, permission transfer, pending-action approval, provider interoperability or real recipient authentication.

## Grants, dry runs and batches

Three governance surfaces in `@stackunseen/ui/conversation-flow` (load `conversation-flow.css` once) extend the single approval into the shapes agents now need.

`ScopeGrantList` shows standing permissions: each `ScopeGrant` carries `id`, `version`, `scopes`, `target`, `grantedAt`, optional `grantedBy`, `expiresAt`, `uses` as a `Measurement<number>`, `maxUses`, `status` (active, expired, revoked, revoking, unknown) and the `sourceProposalId` it came from. Expiry text is derived from the host clock passed as `now`, never the browser's. Revoke sends `{ grantId, version }` and the grant reads "Revoking" until a receipt keyed by the grant id settles. An approval that offers "allow for this session" should create a grant bound to the proposal's `actionDigest` and scopes, never wider.

`DryRunPreview` lists the agent's declared effects (`kind` file, record, message, money or external, `label`, `target`, `reversible` true, false or unknown, optional `detail`) before anything runs. Each line has a Skip checkbox; the one decision carries `planId`, `version`, `run` or `cancel` and the `skippedIds`, and the host re-plans. The summary counts what would run, what cannot be undone and what has unknown reversibility. `stale` blocks the decision when the host has a newer plan version. This is distinct from ReviewChanges, which reviews changes after the fact.

`ApprovalBatch` decides several proposals at once. Only pending, unexpired, included proposals are covered, and only when every proposal shares one target and one scope set; otherwise the batch refuses and asks for single decisions. Superseded and expired proposals stay listed, struck through, and leave the batch. The decision names each covered proposal by `proposalId`, `version` and `actionDigest`; the host's receipt may list `covered` ids and each row then reads "Covered by the receipt" or "Not confirmed by the receipt".

## Reading other protocols

`@stackunseen/ui-core` normalises two human-in-the-loop protocols as read on 2026-10-16. For AG-UI, `readAgUiInterrupts(runFinished)` extracts the interrupts from a `RunFinished` event's interrupt outcome; `fromAgUiInterrupt(interrupt, { runId })` turns `tool_call` and `confirmation` interrupts into an `ApprovalProposal` (version 1, a digest over the interrupt, `allowsEdits` when the response schema offers `editedArgs`, `expires` false when no expiry was given), `input_required` with a flat primitive schema into AIForm-style fields, and anything else into a clarification built from the message; `toAgUiResume(request, answer)` writes the `resume` entry with denials inside the payload and edits only when allowed. For MCP, `fromMcpElicitation(params, { serverName })` reads form mode into fields and url mode into `{ url, host, elicitationId }` so the host can show the domain and ask for consent before navigating (https only), and `toMcpElicitationResult` returns accept with coerced content, decline or cancel. `fieldsFromSchema` maps string, number, integer, boolean and string enums (with or without titles) to fields and reports arrays and nested objects as unsupported.
